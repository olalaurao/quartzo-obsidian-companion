## Operating contract and scope

Companion is local-first where an external filesystem already transports the vault. Otherwise optional API sync uses exactly one DriveSyncCoordinator with three-way baselines; Manual never auto-reconciles, Automatic enables its existing triggers. Credentials and canonical vault content are not stored in a parallel database.

The existing owner must efficiently inventory large vaults; compare path, SHA-256, baseline, remote identity, changed state and trashed state; limit concurrent hashes; and revalidate mutable evidence. Only files in the canonical allow-list are eligible. Never treat a missing baseline or stale owner as permission to overwrite.

Any ambiguous-identity cleanup or adoption requires explicit user intent, fresh snapshot/hash and capability checks, trash rather than permanent deletion, `trashed=true` postcondition and at least one canonical candidate retained. Pairing divergence is fail-closed. Incremental changes, remote duplicates, rename/delete and pending state must reconcile without silently choosing a winner.

The adapter owns finite network request deadlines and quota-aware cooldown/retries. The coordinator owns real observable progress, error recovery and persistent local state hydrated at startup including Manual mode. A retry/restart must not fabricate success.

## Detailed original obligations — verbatim, now with stable identifiers

**C-GUID-09 — Limpeza de identidade ambígua no pairing:** o Companion só pode oferecer limpeza automática de candidatos duplicados após ação explícita do usuário e prova por SHA-256 de que a remoção é segura. A ação deve revalidar o snapshot local/remoto imediatamente antes da mutação, mover candidatos apenas para a Lixeira do Google Drive (nunca apagar permanentemente) e manter pelo menos um candidato canônico por caminho. Caminhos sem resolução inequívoca permanecem bloqueados para revisão manual.

**C-GUID-10 — Quota temporária do Drive:** pairing/sync explícitos não devem tratar limite temporário por minuto da API do Google Drive como falha de autenticação. O cliente deve aguardar/repetir com backoff sem fazer mutações inseguras; uma nova tentativa não deve desperdiçar trabalho já comprovado de arquivos remotos inalterados. Se a quota continuar esgotada após o orçamento de retries, a operação inteira deve parar com erro temporário explícito, em vez de repetir a espera arquivo por arquivo.

**C-GUID-11 — Progresso do primeiro pairing:** após `Accept & Pair`, a UI deve permanecer explicitamente ocupada até a operação terminar. O usuário precisa ver as fases de revalidação, baseline, adoção/upload local, pull remoto e finalização; ações de confirmação/cancelamento que possam iniciar outra operação ficam desabilitadas durante a mutação. O coordenador é a fonte de verdade do estado transitório do pairing, portanto navegar para outra tela e voltar não pode oferecer um segundo pairing concorrente. Ao concluir ou falhar, a tela de Sync deve ser re-renderizada para não exibir estado antigo.

**C-GUID-12 — Falha observável no primeiro pairing:** uma falha após `Accept & Pair` não pode fechar silenciosamente a superfície de pairing nem depender apenas de `Notice` temporário. O motivo completo deve permanecer visível e copiável até ação explícita do usuário, e a tela de Sync deve continuar mostrando o último erro de pairing enquanto o dispositivo permanecer não pareado. A tela de Sync também deve exibir a versão carregada do Companion para diagnóstico de atualização.

**C-GUID-13 — Uma única superfície para o primeiro pairing:** diagnóstico de divergências/ambiguidades, confirmação de limpeza segura, progresso da limpeza, rescan, resumo final, `Accept & Pair`, progresso da aplicação e erro final devem acontecer na mesma superfície visual. Não abrir confirmação nativa ou outro modal por baixo/por cima da superfície de pairing. Cada fase substitui o conteúdo da mesma janela; o usuário nunca deve precisar fechar uma tela para alcançar a próxima.

**C-GUID-14 — Pós-condição da limpeza de duplicados:** mover um candidato para a lixeira do Drive só conta como sucesso quando a API confirmar `trashed=true`. O inventário de pairing deve ignorar recursos marcados como `trashed` mesmo se uma listagem atrasada ainda os devolver. Se a limpeza não puder confirmar a pós-condição ou o rescan ainda reportar um ID recém-movido como ativo, a mesma superfície deve preservar o erro completo; não voltar silenciosamente para `Pairing blocked`.

**C-GUID-15 — Permissão de lixeira em duplicados do Drive:** o diagnóstico de candidatos ambíguos deve carregar `capabilities.canTrash`. O plano automático só pode incluir em `trashFileIds` candidatos com `canTrash === true`. Quando os bytes são idênticos, um candidato que não pode ser enviado à lixeira deve ser preservado como `keepFileId`; se mais de um candidato necessário para a limpeza não puder ser enviado à lixeira, o caminho permanece bloqueado para resolução manual. A capability deve ser revalidada junto com ID/modifiedTime/hash antes da mutação.

**C-GUID-16 — Escopo canônico do vault é allow-list:** sync/pairing do Companion só considera `*.md`, `*.base`, `_attachments/**`, `_capture_ingress/**`, `_deleted/**` e partições contratadas de `sessions/activity_history_v1/**/activity_events_*.jsonl`, além das exclusões já definidas. Arquivos auxiliares de outros domínios no Drive não viram conteúdo do vault só por estarem temporariamente dentro da pasta selecionada. Em particular, Google Workspace nativo (`application/vnd.google-apps.*`) não é arquivo raw-byte do vault e deve ser ignorado pelo pairing/reconciliation, nunca baixado com `files.get alt=media`. O Google Sheet canônico de Finance é propriedade exclusiva do domínio Finance e não participa do Obsidian sync, inclusive durante migração legada de localização.

**C-GUID-17 — Revalidação do primeiro pairing usa o estado atual seguro:** o resumo exibido continua sendo a confirmação do usuário, mas a aplicação não deve exigir igualdade cega com o snapshot antigo quando não há mutação destrutiva. Se um item antes `identical` mudou dos dois lados e os bytes atuais ainda convergem para o mesmo SHA-256, o Companion pode estabelecer o baseline atual. Se um `local_only` ganhar um remoto byte-idêntico ou um `remote_only` ganhar um local byte-idêntico antes da aplicação, deve estabelecer baseline sem upload/pull desnecessário. Qualquer divergência atual, desaparecimento inesperado ou aparição com bytes diferentes continua fail-closed e deve preservar os bytes locais, com erro específico para rescan/revisão.

**C-GUID-18 — Changes API não redefine lixeira como conteúdo vivo:** o feed incremental do Google Drive deve solicitar e propagar `file.trashed`. Um change com `trashed === true` representa ausência remota para um arquivo já rastreado e deve ser ignorado como candidato de identidade quando não rastreado. Recursos na lixeira nunca podem gerar `Ambiguous incremental remote identity`, mesmo se ainda aparecerem no histórico do Changes API após uma limpeza segura de duplicados.

**C-GUID-19 — Owner incremental persistido deve ser revalidado antes de declarar ambiguidade:** quando o estado local guarda um `remoteFileId` para um caminho e o Changes API entrega outro ID para esse mesmo caminho, o coordenador não pode assumir automaticamente que há dois candidatos vivos. Primeiro deve revalidar o ID persistido no Drive. Se ele estiver na lixeira, removido, fora do vault, fora do escopo canônico ou tiver sido movido para outro caminho, ele é um owner obsoleto: preserve os hashes/baseline do estado, descarte apenas a posse daquele ID e reconcilie o candidato vivo pelo three-way normal. Só dois IDs atualmente vivos no mesmo caminho canônico constituem `Ambiguous incremental remote identity`.

**C-GUID-20 — Operações demoradas precisam ser observáveis:** qualquer operação iniciada pelo usuário que possa levar tempo perceptível (por exemplo pairing/rescan, limpeza segura, `Sync now`, full reconciliation, inventário grande, hashing/download de muitos arquivos ou outra rotina multi-etapa de rede/disco) deve deixar claro que continua viva. A UI deve mostrar o nome da operação e a fase atual; quando o total for conhecido, mostrar `concluído/total` e porcentagem derivada do progresso real; quando o total não for conhecido, usar estado indeterminado sem inventar porcentagem. Sempre que possível, mostrar também atividade recente/tempo decorrido suficiente para diferenciar “ainda trabalhando” de “sem progresso aparente”. O estado deve permanecer visível durante toda a operação, sobreviver a re-renderização/navegação da superfície correspondente e terminar explicitamente em sucesso ou erro. Não deixar apenas um botão parado, spinner sem contexto ou `Notice` efêmero para operações potencialmente longas. Não oferecer cancelamento se a operação não puder ser interrompida com segurança.

**C-GUID-21 — Duplicatas remotas também precisam de recuperação segura depois do pairing:** se `Sync now` ou full reconciliation detectar mais de um ID remoto vivo para o mesmo caminho canônico, o Sync Center deve oferecer uma revisão explícita usando o mesmo diagnóstico por SHA-256, `capabilities.canTrash`, revalidação e lixeira reversível já usados no primeiro pairing. O Companion nunca escolhe silenciosamente entre dois candidatos vivos. Quando a limpeza for comprovadamente segura e confirmada pelo usuário, move apenas os duplicados aprovados para a lixeira, rescaneia e roda full reconciliation novamente. Caminhos que não sejam prováveis com segurança permanecem bloqueados e diagnosticáveis.

**C-GUID-22 — Requests do Google Drive têm deadline finito:** nenhuma chamada de rede do adapter do Drive pode manter uma operação de sync/pairing ocupada indefinidamente. Toda chamada deve usar timeout explícito apropriado ao tipo de request; timeout é erro transitório tipado, pode ter no máximo uma repetição curta quando seguro e, se persistir, encerra a operação atual com erro observável para que o lock canônico seja liberado. Upload/download podem ter deadline maior que metadata/listing, mas nunca infinito. O erro deve dizer que a operação foi interrompida por timeout em vez de deixar `Status: Syncing` permanente.

**C-GUID-23 — Modo Manual também hidrata estado local no startup:** recarregar/atualizar o plugin não pode fazer o Sync Center esquecer temporariamente o último sync, baselines, IDs remotos, conflitos persistidos ou inflar `Pending local changes` só porque nenhum sync foi disparado. O estado device-local persistido deve ser carregado durante o startup do plugin antes de a superfície de Sync ser exposta. Essa hidratação é somente leitura local e não conta como sync automático: não faz chamadas ao Drive, não reconcilia e não viola o modo `Manual`. Estado ausente/corrompido deve permanecer fail-closed e observável.
