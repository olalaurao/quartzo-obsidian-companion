# Agents - Companion Architecture

A arquitetura do Companion é dividida nestas camadas:

- **core**: Parsing de objetos, Scheduler, Daily Schedule, Occurrences. Esta camada não depende do Obsidian nem do DOM, idealmente permitindo testes 100% isolados.
- **vault**: Integração com Obsidian. Observa arquivos locais, manipula parse/write e indexação derivadas.
- **sync**: Implementa reconciliação do Drive (push, pull, conflict, baselines) usando estado local isolado.
- **integrations**: Google Auth Loopback para Desktop (sem webview), chamadas à API Drive V3.
- **platform**: Helpers de Obsidian, Lifecycle, Secrets, Notificações do sistema.
- **ui**: Shell do plugin, Home, Planner, Journal, Search, Configurações. Usar Vanilla DOM via Obsidian API, sem react/vue/svelte (a não ser que documentado ganho real).
- **local-state**: Abstração do estado de sincronização e token cache, armazenado localmente (`data.json` para pequeno, file-backed cache para sync queue).

- **OAuth loopback:** O listener desktop deve validar `state` somente em respostas que sejam callbacks OAuth reais. Requests auxiliares do navegador (por exemplo `/favicon.ico`) devem ser ignorados/retornar 404 sem consumir, rejeitar ou encerrar o fluxo de autenticação ativo.

- **OAuth Desktop credentials:** Drive e Calendar devem usar o mesmo `GoogleOAuthDesktop` canônico. O token exchange e o refresh devem enviar `client_id` + a client credential do mesmo Google Desktop OAuth client, mantendo PKCE S256. Release/preflight devem falhar se qualquer uma das duas credenciais de build estiver ausente. Não criar fluxo OAuth paralelo para Calendar/Drive nem commitar valores reais no repositório.

- **Obsidian SecretStorage IDs:** todos os IDs usados em `app.secretStorage` devem vir do owner canônico `src/platform/secret-ids.ts` e obedecer `^[a-z0-9-]{1,64}$` (somente minúsculas, números e hífens; máximo 64 caracteres). Não usar `_`, `/`, espaços ou IDs ad hoc em integrações.

- **Large-vault pairing:** initial pairing must stay linear in the number of vault files. A recursive Drive inventory carries the canonical vault-relative path so pairing/full inventory do not issue parent-metadata requests per file. Pairing may refresh the remote inventory once before mutation, but must never re-run `listAllFiles()` once per local-only or remote-only item. Remote-only classification must not download/hash file bodies until a pull is actually requested. When legacy shared files lack `properties.Quartzo_hash`, the required raw-byte SHA-256 fallback must use bounded concurrency (currently max 8), report live comparison progress, and reuse a proven scan hash at acceptance when remote file ID + modifiedTime are unchanged. Pairing UI must show phase/progress while scanning. If pairing is blocked by ambiguous remote identity, the UI must expose every ambiguous relative path and the distinct Drive candidate IDs/metadata needed for explicit user resolution; a count-only notice is insufficient. Candidate resolution must compare canonical SHA-256 bytes (using bounded concurrency for legacy candidates without `Quartzo_hash`) and report each candidate's relationship to the local file when one exists. Modified time alone must never be used to select an ambiguous candidate.

- **Safe ambiguous-pairing cleanup:** user-triggered cleanup of duplicate Drive identities must be computed by the canonical sync coordinator from SHA-256 evidence, revalidate local hash + remote candidate IDs/modifiedTime/hash metadata before mutation, and route only through the Drive adapter's reversible `trashFile()` operation. Never use `deleteFile()`, newest timestamp, or UI-only heuristics for this cleanup. Always leave at least one candidate per relative path; unresolved paths stay blocked.

- **Drive quota resilience:** per-minute Google Drive quota/rate-limit responses (including retryable 403 quota exhaustion) are temporary network pressure, not authentication failure. Use shared exponential backoff/cooldown, honor Retry-After when present, and retry the individual API request/page that failed. Recursive inventory must never restart an already-completed traversal because one later page was rate-limited. Pairing may keep a reconstructible in-memory hash cache keyed by remote file ID + modifiedTime so repeated scans and partial retries do not redownload unchanged legacy files without `Quartzo_hash`; changing vault identity invalidates that cache. If the retry budget is exhausted, surface the canonical typed temporary-quota error and abort the current pairing pass; never spend the full retry budget independently on every remaining file.

- **First-pairing apply progress:** `DriveSyncCoordinator.applyPairingDecisions()` is the canonical owner of mutation progress and active/inactive state and may expose callbacks/read-only projections for UI only. Report revalidation, baseline establishment, local adoption, remote pull and finalization. The UI must keep the pairing surface visibly busy, prevent duplicate confirmation while mutations are active, show the coordinator-owned active state even after navigation, and refresh the Sync view after completion/failure. Do not create a second pairing-state owner just for presentation.

- **Persistent first-pairing failure projection:** the canonical coordinator owns the last apply failure as transient read-only state alongside active pairing progress. UI may project it in the pairing surface and Sync view, but must not create a second failure owner. An apply failure must remain visible/copyable until the user closes it; ephemeral notices are supplemental only. Sync diagnostics must expose the loaded plugin version so BRAT/release mismatches are observable.

- **Single-surface first-pairing UI:** the plugin owns one `pairingWorkflowModal` surface for the complete first-pairing flow. Duplicate diagnostics, reversible-trash confirmation, cleanup progress, post-cleanup rescan, ready summary, apply progress and persistent failure are render states of that same surface. Do not call a second Obsidian `Modal` or create a parallel pairing dialog from inside the workflow. Closing/replacing one state must never detach the element that later progress callbacks update.

- **Safe-trash postcondition:** `GoogleDriveAdapter.trashFile()` must request and verify the returned `trashed` field; an acknowledged update without `trashed=true` is not success. Drive inventories carry the `trashed` bit and the coordinator defensively excludes `trashed === true`, even when a stale Drive query returns that resource. After safe cleanup, any cleanup error or lingering planned trash ID must stay visible in the single pairing surface rather than collapsing into a generic blocked summary.

- **Drive trash capability is part of safe-cleanup evidence:** ambiguous-pairing inventory must project `capabilities.canTrash` from Drive metadata. `DriveSyncCoordinator.buildSafeDuplicateTrashPlan()` is the canonical owner of permission-aware keep/trash selection and must fail closed for `false`/unknown capability. For byte-identical candidates, preserve the sole non-trashable candidate and trash only `canTrash === true` candidates; if cleanup would require trashing any non-trashable/unknown candidate, leave the path unresolved. Revalidation must compare the capability snapshot before mutation. UI only renders this evidence and must not invent a parallel permission heuristic.

- **Canonical vault file scope:** `src/sync/coordinator/file-policy.ts` is the single owner of sync eligibility for local and remote inventory. Enforce the contract as an allow-list (`*.md`, `*.base`, `_attachments/**`, `_deleted/**`) after canonical exclusions; do not broaden it to arbitrary files because they happen to live under the Drive vault root. Remote candidates must additionally reject Google Workspace-native MIME types (`application/vnd.google-apps.*`), which have no canonical raw-byte representation for the sync protocol. Finance's `Quartzo Finance (Data)` spreadsheet is a separate Finance-domain source of truth and must remain outside Companion vault pairing/reconciliation even while a legacy copy is still located under the vault folder. Do not add name-specific sync heuristics in UI or adapter code; route scope decisions through `VaultSyncFilePolicy`.

- **First-pairing live revalidation:** `DriveSyncCoordinator.applyPairingDecisions()` revalidates the current unknown-base vector immediately before applying. Snapshot drift alone is not an error for a non-destructive baseline: an originally identical item may baseline the current hash when fresh local and Drive raw-byte SHA-256 still match; a local-only/remote-only item that gained an identical counterpart may also baseline without upload/pull. Never use this rule to overwrite a newly divergent counterpart. If current local and Drive bytes differ, or an expected side disappeared, fail closed with a specific diagnostic and leave local bytes untouched. Keep this logic in the coordinator; UI and adapters must not invent parallel drift heuristics.

- **Incremental Drive trash semantics:** `GoogleDriveAdapter.listChanges()` must request/project `file.trashed`. `DriveSyncCoordinator.processChanges()` is the canonical owner of interpreting a `removed=true` change or `file.trashed===true` as remote absence. A trashed untracked resource is not a live identity candidate and must never collide with the retained `remoteFileId`; a trashed tracked resource follows the normal remote-delete/conflict rules. Keep this in the adapter/coordinator path rather than adding UI workarounds or path-name exceptions.

- **Stale persisted remote owner revalidation:** before throwing `Ambiguous incremental remote identity`, `DriveSyncCoordinator.processChanges()` must revalidate the persisted path owner's `remoteFileId` through the canonical Drive adapter. If that owner is trashed, 404/missing, outside the selected vault, outside canonical sync scope, or now resolves to another path, clear only the stale live-ID ownership while preserving the previous baseline/hash vector, then reconcile the incoming live candidate normally. Only two currently live IDs that both resolve to the same canonical path are a true incremental ambiguity. Do not resolve this in UI or by filename heuristics.
